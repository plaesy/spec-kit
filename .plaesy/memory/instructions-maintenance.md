# Instructions Maintenance

Patterns learned during a 2026-10-03 cleanup pass across `instructions/` and
`prompts/`. See `decisions/extract-always-load-bloat.md` for the extraction
decision itself; this file is the "how not to break it again" reference.

## The `.instructions.md` → `.md` suffix trap

Every file under `instructions/*.instructions.md` is installed with the
`.instructions` segment **stripped** — `scripts/internal/scaffold/copy.go:273`
(`copyInstructions`, both `always_load` and `scope_load` loops) and
`scripts/cmd/plaesy/stack.go:102` (`plaesy stack detect --install`) both do
`strings.TrimSuffix(filepath.Base(srcFile), ".instructions.md")`. So
`quality-gates.instructions.md` lands at `.plaesy/instructions/quality-gates.md`.

A cross-reference written as `` `assess-financial.instructions.md` `` (bare,
with the source suffix, no path) points at a file that **does not exist** in
any installed project. The correct form is
`` `.plaesy/instructions/assess-financial.md` `` — full runtime path, `.md`
suffix, no `.instructions`.

This bug was found in ~15 files, dozens of occurrences, all fixed in the
2026-10-03 pass. **When adding any new cross-reference to another
instructions file, use the `.plaesy/instructions/{name}.md` form — never the
bare source filename.** One deliberate exception: `how-to-create-
instructionsmd.instructions.md` citing `angular.instructions.md` as an
*example of the source naming convention itself* (meta-documentation about
the repo, not a runtime pointer) — that one correctly keeps the suffix.

A second, milder form of the same mistake: a bare `` `dimension-mapping.md` ``
with no path prefix. Not wrong (right filename), just ambiguous — prefer the
full `.plaesy/instructions/dimension-mapping.md` for new references, but this
form wasn't worth a repo-wide sweep (lower severity, many legitimate
intra-table short-form uses).

## This repo dogfoods itself — reload after every instructions/prompts edit

This repo has its own `.plaesy/` directory, generated by a prior `plaesy
init`/`reload` and checked into the *working tree* (gitignored, but present
on disk). `internal/scaffold`'s `TestInstalledInstructionsMatchSource`,
`TestInstalledTemplatesMatchSource`, and `TestReloadOnThisRepoIsIdempotent`
compare that live `.plaesy/` against current `instructions/`/`templates/`
source and **fail on drift**.

After editing anything under `instructions/`, `templates/`, `prompts/`,
`agents/`, or `checklists/`:

1. `cd scripts && go run ./internal/assets/gen` — syncs
   `scripts/internal/assets/data/` (the Go-embedded copy; a separate test,
   `TestAssetsDataMatchesSource`, checks this one).
2. Build the CLI and run `plaesy reload` from the repo root — refreshes this
   repo's own `.plaesy/instructions/` and `.plaesy/templates/`.
3. If a `prompts/*.md` file changed, also run `plaesy reload --ai claude` (or
   whichever platform's mirror exists under e.g. `.claude/commands/`) — step 2
   alone does **not** touch platform-specific prompt mirrors; a separate flag
   is required and was missed once this session, leaving 31 stale files in
   `.claude/commands/` (likely stale since before this session, not caused by
   it, but only caught by running this step).
4. `plaesy validate markdown` — the repo is a zero-tolerance ratchet
   (`docs/scripts/plaesy-trim.md`/`internal/mdlint`); a line over MD013's
   200-char limit anywhere fails `go test ./internal/mdlint/...`.

Skipping steps 1–3 doesn't just leave stale generated files — it makes
`go test ./...` fail with real, reproducible errors that look like a code
regression but are actually just an un-synced copy.

## `plaesy reload` resolves its target from the **current directory**

Step 2 above says "from the repo root" for a reason that cost real time on
2026-10-04. `plaesy reload` takes its target from `cwd`, and running it as
`cd scripts && go run ./cmd/plaesy reload` therefore scaffolds a **complete
`.plaesy/` tree inside `scripts/`** — 118 files of instructions, templates,
checklists and scripts — and exits 0 reporting "Reload complete".

Nothing warns you. The tell is in the log: `Refreshing generated files in
.plaesy/ from ...` with a *relative* `.plaesy/`, and a summary of "117 created"
where a reload of an existing project should say "0 created". The same run also
reports the real `.plaesy/instructions/plaesy.md` as "unchanged" while it is in
fact stale, because it compared a different copy.

Correct form — build once, run from the repo root (the same
`./scripts/plaesy.exe` path this index already uses):

```bash
cd scripts && go build -o plaesy.exe ./cmd/plaesy && cd ..
./scripts/plaesy.exe reload . --plaesy-home .
```

`--plaesy-home` is belt-and-braces: `FindHome` resolves from the executable's
ancestors, then `cwd`, so a binary built into a temp dir depends entirely on
where you run it from. `reload --dry-run` first is cheap and shows the target.

**Cleaning up the stray tree is where this gets dangerous.**
`scripts/.plaesy/` already contained a *tracked* file
(`scripts/.plaesy/memory/token-stats.json`), so `rm -rf scripts/.plaesy`
silently staged a deletion of a file the repository tracks. Always
`git status --porcelain` immediately after removing anything, and
`git checkout -- <path>` to restore. The untracked leftovers read as junk; the
tracked one does not announce itself.

## `go test ./... | tail -N` hides the real exit code

`tail`'s own exit code (almost always 0) is what a pipeline reports, not
`go test`'s. Every "tests passed" check this session that piped through
`tail` was reporting a false positive — confirmed by re-running the exact
same point in history without the pipe and getting `FAIL`/exit 1. **Always
capture `$?` immediately after `go test`, before piping its output anywhere**:

```bash
go test ./... > out.txt 2>&1; ACTUAL_EXIT=$?; echo "ACTUAL_EXIT=$ACTUAL_EXIT"
grep -E "^(FAIL|ok)" out.txt
```

(redirect to any scratch file in your working directory — the path itself
doesn't matter, only that `$?` is captured immediately after `go test`,
before anything pipes its output further)

## Fake ordered-list sub-markers (`5a.`, `5b.`) break MD029 numbering

`prompts/implement.md` had a numbered step 5 followed by `5a.`/`5b.`
sub-points, then a step `6.` written as `1.` (copy-paste restart). Markdown's
ordered-list parser does not recognize `5a.`/`5b.` as list continuation —
they read as plain paragraphs, which breaks the list's contiguity and makes
the *next* real `N.` item reset its expected number to 1. The zero-tolerance
MD029 ratchet catches this immediately once the file is touched.

Fix: never use letter-suffixed fake ordered markers. Nest real sub-points as
unordered `-` bullets, indented a multiple of 2 spaces (MD007) under the
parent numbered item — not 3 spaces, even though 3 visually aligns with the
`N. ` marker's text column.

A second instance of the same root cause (duplicate-number restart) was
found and fixed in `prompts/save.md` this session (a step "3. Learning
something" landed before the existing "3. Update context", both numbered 3)
— same fix, renumber sequentially, don't restart.

## A framework-maintainer-only instruction leaking into a consumer-facing prompt

`prompts/implement.md`'s technology-detection steps (1-5, real operational
steps any consuming-project agent can execute) were followed by a step
telling the agent to "add new technologies by editing `instructions/
mapping.json` in source" — a file that **only exists in the spec-kit
framework's own upstream repo**, never installed into any consuming
project's `.plaesy/`. For the overwhelming majority of `/implement`
invocations (an agent working inside someone else's project after `plaesy
init`), that step is not actionable at all — it's an instruction for
whoever maintains spec-kit itself, not for the prompt's actual audience.

Not wrong, just unlabeled: fixed by making the step explicitly say "not
actionable in a typical consuming project" and naming when it does apply
(this session, dogfooding the spec-kit repo itself, is the exception, not
the rule). When writing a prompt meant to run inside arbitrary consuming
projects, flag any step that only makes sense inside the spec-kit repo
itself — don't let framework-authoring instructions blend in with
user-facing ones silently.

## Fictional feature content creeps into instructions files

`universal-orchestrator.instructions.md` had a full section ("10/10 Autonomy:
The Last Gap") documenting `/start --learn-from` and `/assess --predict` as
if they existed — zero hits for either string anywhere in `scripts/` or
`prompts/`. Before trusting a documented CLI flag while editing instructions,
grep the codebase for it. Unreferenced "aspirational" sections (also found:
an "Integration Template" and "Recovery Metrics" section in
`error-recovery.instructions.md` with no references anywhere else in the
repo) are candidates for deletion, not preservation.
