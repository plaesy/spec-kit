# Plaesy Spec-Kit Constitution

**Purpose**: The governing decisions for this specific project. Every later phase
(`/assess`, `/implement`, `/optimize`, `/improve`) reads this file before acting —
it is the single source of truth for standards that would otherwise be re-decided
(and re-litigated) on every run.

> Generated by `/optimize` bootstrap (constitution was missing). Amend deliberately
> via `/save` — do not let downstream phases silently drift from what's written here.

## 0. Active Dimensions

Plaesy Spec-Kit itself is a multi-dimension framework (`/assess`, `/improve`,
`/optimize`, `/fix`, `/implement` all support technical, design, business, legal,
marketing, financial, management, and product scopes) — this project should not be
constitutionally restricted to software alone just because its own tooling happens
to be shell scripts. All eight dimensions below are **active**; a phase run without
an explicit `--scope` should consider every dimension relevant to the artifact in
front of it, not default to technical-only.

| Dimension | Status | Notes |
|---|---|---|
| Technical | Active | Core of this repo — see §1/§2 |
| Design | Active | Prompt/instruction/template authoring quality, docs UX, CLI ergonomics |
| Business | Active | Framework's own adoption/value proposition as a product (spec-kit-for-spec-kits) |
| Legal | Active | License compliance (LICENSE, CODE_OF_CONDUCT.md, SECURITY.md), contributor terms |
| Marketing | Active | README/docs positioning, messaging to prospective adopters |
| Financial | Active | Contributor/maintainer time cost, no paid infra to track today |
| Management | Active | CONTRIBUTING.md process, issue/PR triage, release cadence |
| Product | Active | Roadmap/CHANGELOG, feature prioritization across the 11 prompt phases |

Dimensions with no concrete finding yet are still active — "N/A this run" (see
`/improve`'s Spec Quality rule) is a valid per-run result, but the dimension itself
should not be dropped from scope.

## 1. Quality Standards (Technical)

- **Test coverage minimum**: 90%
- **Performance target**: Shell scripts (bash/powershell) complete detection/init routines in <2s on a typical repo
- **Security bar**: zero known vulnerabilities at Sev-High or above
- **Documentation bar**: complete for all public interfaces (prompts, instructions, scripts)

## 1b. Quality Standards (Other Dimensions)

- **Design**: every prompt/instruction/template ships a usage example; no orphaned
  file (unreferenced from any prompt, instructions, or docs/ index)
- **Business/Product**: CHANGELOG.md updated for every user-visible change; no
  feature merged without an entry point from at least one prompt phase
- **Legal**: LICENSE/CODE_OF_CONDUCT/SECURITY.md kept current; no dependency added
  without a compatible license
- **Marketing**: README stays accurate to actual current capabilities (no
  aspirational/undelivered feature claims)
- **Financial**: no paid third-party service introduced without an explicit
  maintainer decision logged in this file's Amendment Log
- **Management**: CONTRIBUTING.md reflects the actual current contribution/review
  process; no undocumented process change

## 2. Technology Constraints

- **Approved stack**: Shell (Bash + PowerShell parity required), Markdown-based prompt/instruction templates, Git
- **Forbidden/deprecated**: none identified yet
- **Validation source**: Context7 (or equivalent) citation required for any new dependency

## 3. Process Rules

- **TDD**: Required where practical — Red-Green-Refactor, tests before implementation
- **Review gate**: implementation is not "done" until a verifier pass (independent of
  the implementing agent/session) checks the diff against the spec — see `/implement`.
- **Ambiguity handling**: unresolved ambiguity blocks `/implement`; run `/assess` first
  (Mode 1 resolves spec ambiguity, not just external research).
- **Bash/PowerShell parity**: any bug fixed or feature added on one side must be fixed/added on the other.

## 4. Non-Negotiables (Hard Stops)

- Never store secrets or credentials in source control
- Never disable a failing test to make CI pass
- Never let `plaesy analyze` overwrite existing `.plaesy/context.md` / `.plaesy/memory.md` content
